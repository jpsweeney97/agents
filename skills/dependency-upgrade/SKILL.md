# Dependency Upgrade

Absorb one upstream dependency version bump safely, end to end. Invocation: `/dependency-upgrade` or `$dependency-upgrade`.

A forcing pass over one chosen bump — a named dependency from its current version to a target — that discovers what actually changed upstream, resolves what the bump forces onto this repo, proves it by behavior, and stops at the lines where the bump exceeds a mechanical absorb. It executes the bump on a working branch; it never pushes, opens a PR, or publishes unless asked.

## Shape — a forcing pass over one bump

**Confirm the ecosystem first** — a required first step, not a courtesy. State the package manager and its manifest/lockfile pair (npm/pnpm/yarn, pip/uv/poetry, cargo, go modules, maven/gradle, bundler, composer) and the test/lint gate, because resolution and proof mechanics differ by ecosystem. Reason about the manager-invariant *concepts* and name exact commands only for the confirmed manager at hand — **never a cross-manager command table**. State the dependency, the current version read from the **lockfile** (not the manifest range), the target, and *why* the bump (feature, forced transitive floor, peer requirement) — it sets the stop thresholds.

Then walk the pass, each step a forcing question, not a fill-in:

- **Gate the version before pulling.** Confirm the exact target is safe to fetch, scoped to what is *checkable*: it exists and is not yanked/deprecated/retracted; the resolver pins it to a recorded integrity hash; the name is not a typosquat-adjacent variant; and pulling it runs no install hooks until accounted for (inspect first; resolve with install scripts disabled until cleared). Make only claims you can establish — do **not** assert maintainer-history or provenance you have no source for; surface those for a human to judge, never record a vetting assurance you did not verify. Depth scales with risk: a patch bump of a present dependency at a known-good hash is a light pass; a new dependency or a major jump gets the full check. Unverifiable or suspect → **stop before pulling**.
- **Read the change record across the whole range.** Read the upstream CHANGELOG / release notes / migration guide for current→target, *not the target alone*, and do not let a semver label stand in for the read. Depth scales with drift: a current bump with a consolidated upstream guide is a disciplined read of that guide plus a catch for deprecations it omits at intermediate versions; a long-neglected bump with thin notes deepens into tag-diff and tracker archaeology. Extract each breaking delta with a one-line source pointer; a note you cannot find is residual risk, never assumed safe. If the range crosses more than one major and the upstream guide assumes one-major-at-a-time, plan a **stepped path** through intermediate versions rather than leaping into a state no guide describes — a single-major bump is one step, no invented ceremony.
- **Map the blast radius into this repo.** Borrow the breaking / additive / behavior-preserving classification *pointed upstream*: for each material delta, find what here touches the changed surface (`path:line`) and ask *does this fix exceed mechanical?* An `rg` sweep is evidence, never an exhaustive consumer list. This yields the routing call below.
- **Apply and resolve the tree.** Make the manifest change, run the resolver, and **scope the lockfile diff** to the intended dependency and the transitive closure the bump forces — account for every pin that moved; surface whole-tree drift rather than accepting it. A peer/version conflict resolvable only by a forced override that hides a real incompatibility is a **stop**, not a fix.
- **Route the call-site fixes by shape.** Never force one route: a *uniform* mechanical change across many like sites → hand the now-discovered change to `migration-campaign` as its supplied input; *many distinct bespoke per-delta edits* → sequence the discovered deltas into an ordered plan (this skill found them, so it owns the sequencing) and hand that plan to `execute-plan`, which runs from a plan, not a loose edit list; a *small local* fix → apply inline; a *refactor-scale* change beyond mechanical fixes → **stop and surface**. Naming all four prevents a heterogeneous bag of fixes from being mis-driven into a uniform-sweep tool or silently absorbed by the back-to-green loop.
- **Prove by behavior, then close.** Run the real build + test + lint — real commands, real output. Green is the **floor, not the proof**. Then probe the gap green hides, *bounded so it can actually close*: the deprecation/removal warnings the build emitted; the behavior-changed paths from the range read **intersected with the call sites this repo actually reaches**, severity-ranked, highest first; and the transitive shifts from the resolve step. Drive incidental red back to green via `keep-green`; hand unclear-cause breakage to `diagnose`. Render exactly one verdict: **safe-as-proven** (the bounded high-severity gap was probed and the residual is named — never "no residual exists") / **unsafe-here-because** / **unverified** (with the exact check a human must still run; never round up to safe).

Close by **checking the footguns off** explicitly: ecosystem confirmed; version gated; whole range read (not target-only); majors stepped; lockfile diff scoped and accounted; no conflict masked; fixes routed by shape; proof covers the bounded behavior gap and deprecations, not green alone; verdict and residual stated. An unchecked footgun is the finding. **Completeness is held by this checklist, not by luck:** every delegation (the sweep to `migration-campaign`, the bespoke plan to `execute-plan`, the repair loop to `keep-green`) is fire-and-return — control resumes at the next owned step, and the behavior-proof and this checklist are owned *here* and run *after* the sub-run returns. The most fragile seam is a long delegated sweep on a multi-major bump: do not let it become the green-only relapse this skill exists to prevent.

## Modes and scope

- **Applied vs advisory follows the invocation.** "Plan the React 18 upgrade" is advisory — produce the version gate, range read, blast radius, and path before any edit. "Do the upgrade" executes within bounds: apply the manifest bump, run the resolver, scope the lockfile, apply small bespoke fixes inline, and prove it. Default to the mode the context implies; ask once when genuinely ambiguous. Applied mode does not dissolve the judgment — surface each conflict-resolution and path choice as a flagged decision in the diff, not a default silently baked in.
- **One bump.** Default scope is one dependency to one target. Pointed at a whole dependency list or a dependabot wall, narrow to the named or riskiest bump(s) and *say so* — this is a forcing pass, not an audit. A scored backlog of stale-dep debt is `tech-debt-scan`'s job.

## Proof boundary (the inherited floor)

This is the library-wide evidence-before-claims floor specialized to absorbing foreign code. Never fabricate a change-record entry, a resolver output, a version-safety verdict, or a "tests passed"; report only what the real gate produced. Where a behavior path cannot be proven locally, render `unverified` with the exact residual named, never a green stamp over a gap merely glanced at. State what was verified and bound the residual: *"read the 17.x→18.0 range and classified the breaking deltas; bumped and resolved with the lockfile diff scoped to React and its peers; green on the suite plus a read of the three highest-severity behavior-changed paths the notes flagged — not run against the full app, not confirmed in production."* Never inline secrets or registry credentials.

## Fences

- **vs `migration-campaign`** (the sharpest collision — its description already claims "framework/API call-site bump"). The line is **change-discovered vs change-supplied**, resolved by **routing the fix by shape**. `migration-campaign` takes the change as supplied and owns the burndown for one *uniform* edit across many like sites; this skill *discovers* what the upgrade requires from upstream notes and hands a uniform sweep to it as a now-supplied change. A bag of *distinct* per-delta fixes is not a campaign — sequence it into a plan and route that to **`execute-plan`**. The loader cannot tell these apart from the prompt alone; the determination is yours after the range read.
- **vs `contract-change-propagation`.** Inverse direction and mode: it maps *your own proposed* interface change forward, read-only, and stops at a plan. This runs the consumer side of an *already-shipped upstream* change and it *executes*. Borrow its classification technique pointed upstream; do not become it or re-derive it for an in-house change.
- **vs `tech-debt-scan`.** It flags *which* deps are stale as backlog findings and routes security/CVE signal out; never upgrades. This absorbs a *chosen* one — a scan finding is a valid trigger, the scan is not this skill.
- **vs `keep-green`.** The bounded back-to-green repair helper this skill delegates to; it owns no change-record read, no resolution, and stops *at* green, where the behavior-proof begins.
- **vs `migration-safety`.** Name collision only — DB schema/data migrations against a live database, zero package-dependency content. If the prompt is about a database migration, it is the other skill.
- **vs `deploy-plan` / `release-cut` / `diagnose`.** Hand the rollout go/no-go, abort thresholds, and bake window to `deploy-plan`. `release-cut` bumps *your* package's version and changelog — the producer end of the version relationship, unrelated to consuming a bump. Engage `diagnose` only when a post-bump break has an unclear cause; this owns the upgrade, not the root-cause hunt.
- **Supply-chain.** The version gate is a narrow pre-pull trust-to-fetch check on the one chosen version, scoped to what is checkable — *not* the parked repo-wide security audit and *not* `red-team`'s attacker-intent modeling.

## Done when

- The ecosystem and tooling are confirmed; the dependency, current (lockfile) version, target, and reason are stated.
- The exact target version was gated before pulling (or stopped as suspect/unverifiable), scoped to checkable facts with no recorded assurance the agent could not source.
- The whole current→target range was read (not target-only, semver refused as oracle), each breaking delta classified with a source pointer, and any multi-major path stepped.
- The lockfile diff is scoped to the intended dependency and its forced closure, every moved pin accounted, no conflict masked by a forced override.
- Call-site fixes are routed by shape (uniform → `migration-campaign`, bespoke → sequenced into a plan for `execute-plan`, small → inline, refactor-scale → stop), with the behavior-proof and this checklist owned here after any delegate returns.
- The upgrade is proven by behavior — green plus the bounded suspect∩reached behavior gap and build deprecations — and exactly one verdict is rendered: *safe-as-proven* / *unsafe-here-because* / *unverified*, with the residual bound stated.
- Delivered in the mode the invocation implies: an advisory run ("plan the upgrade") is done at the version gate, the cross-range read and classification, and the stepped path — it stops before resolve/route/prove; an applied run additionally completes the lockfile, routing, and behavior-verdict bullets above. Either way, work stayed on a working branch and nothing was published unless asked.
