# Skill-Use Contract + Composition Data Layer — Design

Status: patched per six review rounds — five on 2026-07-11 (three `review-reviewer` adjudications; the fourth pinned the edge-census method, the fifth generated the census as a committed artifact) plus a sixth adjudicated via `review-reviewer` on 2026-07-12, whose delivery objection was refuted by a live probe (recorded under Controlled delivery) and whose confirmed findings land here: a sealed no-overfire calibration gate, environment-surface enumeration, a sealed trial schedule, an effective-load canary, and a data-layer coverage table (see Review Disposition). Design approved by JP 2026-07-12. This document is also the durable evidence artifact the charter Admission will cite.

## Problem

Two observed failure modes in how Claude Code and Codex leverage the global skill library (~90 skills served from `~/.agents`):

- **Silence** — no skill invoked when one fits the task. Observed repeatedly by JP across sessions (specific instances unrecorded); notably, on the Claude side these failures happened *with* the harness's own skill-matching instruction loaded (see Premise, below).
- **Missed composition** — a single skill invoked when a sequence or parallel combination would serve better. One directly observed case plus seven never-observed-leveraged sequences, inventoried below.

Non-goals: request-time skill matching, which is fixed runtime terrain; routing speed; rival-vs-rival misrouting (never observed). Constraints fixed during shaping: the mechanism must be ambient/always-loaded for the moments it owns (mid-task re-checks, handoffs, and composition) and must reach both runtimes. Bar: highest plausibility of success, not formal verification. Accepted trades: every-turn context cost in both runtimes, and the charter gate for always-loaded contracts.

## Premise (honest headwind, named)

Both runtimes carry request-time skill-matching terrain at design time: Claude's harness system prompt has a blocking request-time matching instruction (re-verified first-hand each review round), and the current Codex runtime is reported to require use of an available matching skill — a claim with no recorded evidence pointer yet, to be verified against the live Codex runtime at build before the Admission consult (Build Order step 2); if it fails, the narrowing reopens for the Codex copy, with runtime-divergent text as the named fallback at the cost of the byte-identical canary. The local contract therefore does not restate or reinforce request-time matching. It owns the moments that terrain does not: a finding changes the needed work mid-task, an invoked skill reaches a named handoff, or one task spans multiple skill jobs. Ledger context: fires are 86% user-initiated in the 4,276-record review snapshot (3,686 user vs 590 model), but the split varies sharply by skill — `tdd` fires 23/25 model-initiated — so model-initiated invocation is possible; the open question is whether the local mid-task/handoff/composition obligations materially improve followership.

## Design

### 1. The contract (procedure layer)

A byte-identical `## Skill Use` section in both `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`. Draft — the wording passes through the `agent-facing-design` and `writing-principles` gates at build (Build Order step 2) before landing:

> ## Skill Use
>
> - When a mid-task finding changes what the work needs, re-check whether an available skill owns the newly revealed work; when one plausibly fits, invoke it rather than improvising the same job unaided. The check is silent — don't narrate it.
> - When an invoked skill completes and names a follow-on lane — an exit, handoff, or next-step pointer — take it only when the current request and governing skill authorize continuation; otherwise offer it explicitly. Don't drop the chain and improvise the next step.
> - When a task or its findings span more than one skill's job, compose the skills rather than stretching one past its boundary. Composition may be sequential or concurrent, but it does not itself authorize subagent fan-out.
> - A governing skill's explicit stop, containment, or sequencing instruction overrides these defaults, and delegated agents follow their brief.

Design choices: the first bullet is mid-task-only, leaving request-time matching to fixed runtime terrain; "plausibly fits" keeps the re-check sensitive to the observed silence failure, while the mid-task trigger and silent check bound its reach. The second bullet preserves permissioned handoffs: continuation requires authority, otherwise the skill is offered by name. The third describes workflow composition without granting delegation authority. The final bullet makes governing-skill stops and delegated briefs controlling.

### 2. The data layer (exits in bodies, edges in descriptions)

Forward handoffs land in skill **bodies** as exits (the `outcome-shaping` Exits-table pattern, `SKILL.md:78`); **descriptions** change only where selection-critical, per the existing frontmatter convention. Touched skills, recomputed from the pinned body-level census (fifth round, per the committed census artifact): `diagnose` (carries a description-level handoff — `diagnose`→`tdd` — that gets a body exit), `tdd`, `test-trust-audit`, `red-team` (parallel fan-out), `postmortem`, `observability-instrumentation`, `deploy-plan`, `behavior-smoke-test`, `scrutinize-skill`; description edit for `making-recommendations` (thin-field → `ideate`, selection-critical per the observed miss). Dropped from the earlier list because their body edges already exist: `characterization-tests` (`SKILL.md:39`), `contract-change-propagation` (`SKILL.md:43`), `skill-squad` (`SKILL.md:70`), `ideate` (`SKILL.md:44`), and — fifth round — `incident-response` (both edges already in its body: →`diagnose` at `SKILL.md:29`/`:93`, →`postmortem` at `:94`/`:106-107`; the fourth-round census missed the second). Special cases: `scrutinize-skill` is plugin-distributed (`review-family`) — Class-B publish path (version bump → Codex republish → mirror) on JP's ask; chain-7 exits naming Claude-only skills get availability-conditional phrasing. These edits are build-and-prune, not charter events.

### 3. The convention (repo `AGENTS.md`, Skill Editing section)

One line, roughly: when a skill's work has a natural upstream or downstream lane, name the handoff in the body — an exits line or section, availability-conditional for single-runtime lanes — and add it to the description only when selection-critical. This repo-local always-loaded edit may share the contract's Admission consult but remains a distinct decision. Scope note for the admission: this is editing guidance about *where* handoffs live; `agent-facing-design` keeps the routing-design judgment job untouched.

## Charter Package

One Admission consult may cover both gated edits, but it must adjudicate them as two distinct decisions and record one ledger entry per decision in `contract-decisions.md`.

### Decision A — runtime skill-use contract

**Q1 — closest existing contract:** the closest contracts are the runtimes' own request-time skill-matching instructions. They retain that job. The local contract begins only when a mid-task finding changes the work, when an invoked skill reaches a named handoff, or when one task spans multiple skill jobs. `work-router` owns explicit routing questions and is neither duplicated nor retired by this design.

**Q2 — what failure lighter context would not prevent:** one directly observed composition miss occurred despite the relevant handoff already existing in a skill body, while the broader ledger pattern supplies only a hypothesis because it lacks an opportunity denominator. The proposed four-bullet instruction section is the lightest ambient form that can govern the unowned mid-task and seam moments. Admission remains conditional on the prospective probes; aggregate counts alone do not clear it.

**Q3 — houses standards:** the contract is runtime-neutral, names its three owned moments, preserves authorization and governing-skill stops, and says plainly what an agent must do.

### Decision B — repo skill-authoring convention

**Q1 — closest existing contract:** `agent-facing-design` owns whether a routing or handoff relationship belongs in a skill; the repo convention owns only where an already-decided handoff is written — body by default, description only when selection-critical, and availability-conditioned for single-runtime lanes. It does not make the routing decision.

**Q2 — what failure lighter context would not prevent:** the inventory shows handoff data split inconsistently between bodies, descriptions, and non-route boundaries. One line in repo `AGENTS.md` is the lightest durable context for future skill authors; no validator or additional workflow is justified.

**Q3 — houses standards:** the line points routing-design judgment back to `agent-facing-design`, states the body/description placement rule, and carries the dual-runtime availability boundary.

**Subagent exposure (review M2), priced and accepted:** user-global instruction files load into most subagent contexts — general-purpose, custom, and workflow agents; the built-in Explore and Plan agents are the documented exceptions and skip CLAUDE.md entirely (sub-agents doc, "What loads at startup") — so the contract binds those delegated workers and any eval control arms run through them; the delegated-agents clause scopes narrowly-tasked delegation to its brief, the residual exposure is named here for the admission and watched via the usage ledger, which demonstrably captures subagent fires (47 `sidechain: true` records at design time) — and pre-registered evaluations in this repo must account for the ambient contract when defining control baselines.

**Durability:** the canonical contract text lives as `CANON` in a new drift-check script (`check-protected-set.sh` pattern) checking both global files byte-identically. The build must wire that script into tracked `.codex/hooks.json`, ignored `.claude/settings.local.json`, and the recovery recipe in `scripts/claude-skills-sync.sh`; losing the ignored Claude settings must not silently remove the check. Reach is repo-session-triggered, not ambient: the check runs when a session starts in `.agents`, so drift between such sessions surfaces only at the next one — the same accepted reach as the existing protected-set canary. This committed design doc is the Admission evidence pointer for the observed failures, bounded ledger analysis, and probe design.

## Proof Plan (pre-landing probes)

Pattern: `docs/agents/contract-evaluation-methodology.md` moves 1, 2, 3, 6, and 7 — pilot before seal, adversarial prereg review, seal-by-commit, single-variable differential, blinding, immutable surfaces, and replicated escalation. The prior plugin admissions were single-arm forward tests and are not precedent here. Spec:

- **Controlled delivery:** each trial is a `claude -p` subprocess with `--output-format stream-json`, a pinned CLI binary (`claude --version` recorded in the seal, auto-update disabled for the run; a mid-run version change invalidates the affected trials), a fixed model, fixed setting sources, fixed permissions/tools/environment, and one of two scratch `CLAUDE_CONFIG_DIR` trees. The trees contain identical seeded settings, skills, and skills-directory plugins; the only arm difference is the contract block in the user-global instruction replica. Seeded settings exclude the production skill-usage ledger hook: it writes to the `$HOME`-keyed live ledger (`scripts/skill-usage-hook.py` → `~/.claude/logs/skill-usage-ledger.jsonl`), so trial fires would contaminate the dataset the 2026-08-01 watch reads — takes are captured from each trial's own `tool_use` stream instead. Delivery evidence (2026-07-12 adjudication probe, CLI 2.1.207): a scratch `CLAUDE_CONFIG_DIR` tree's `CLAUDE.md` demonstrably loads in headless runs and shadows the real `~/.claude/CLAUDE.md` (marker present, host-file content absent; empty-tree control negative; the probe quoted the tree file's heading unprompted), and Keychain-held authentication survives the scratch tree. The official docs document only `~/.claude.json` relocation for `CLAUDE_CONFIG_DIR`, so this is undocumented behavior: the effective-load canary below re-proves it per tree, and the version pin bounds drift. Both arms retain the runtime's fixed request-time matching terrain. Fixture skill sources are pinned: pre-data-layer versions (probes run before Build Order step 10), except that both trees seed the planned `diagnose` body exit to `tdd`, drafted early for the fixture and identical across arms — single-variable holds — so the seam probe scores the contract's response to a body-named follow-on, the configuration that will exist post-landing; the description-only variant of the seam is deliberately not covered.
- **Roster and surface proof:** parse every run's `system/init` event and require the exact expected target-skill roster before scoring. Before the pilot and again before sealed runs, hash both instruction replicas, every loaded target skill source, plugin manifests, settings, task fixtures, and the workspace fixture manifest; the hash record includes the CLI binary identity (`claude --version` output) and all controllable effective configuration, not only the tree files. A roster or hash mismatch invalidates the run rather than counting as contract failure.
- **Effective-load canary:** disk hashes and roster checks do not prove the instruction replica entered the effective prompt. Before the pilot and again immediately before sealed runs, a non-scored headless run in each tree must quote the first heading of its loaded user-global instructions (byte-matched against the tree's replica), report a distinctive host-file phrase absent, and confirm the `## Skill Use` heading present in the ON tree and absent in the OFF tree. The canary is run by the arm-map holder, never the scorer; a canary failure blocks all trials in that tree.
- **Environment surfaces (unconditional inputs, enumerated):** inputs that load regardless of setting sources are disabled or recorded in the preregistration: auto memory disabled via `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in the trial environment (it loads into the system prompt regardless of setting sources, and its storage path may be `$HOME`-keyed rather than tree-keyed); claude.ai MCP connectors suppressed via `disableClaudeAiConnectors: true` in the seeded settings, with their absence confirmed against the pilot's `system/init`; managed and server-managed settings checked for on the host, with presence or absence and content hashes recorded; and the authentication method recorded (the delivery probe shows Keychain auth reaches scratch trees).
- **Immutable fixtures:** each trial starts from a fresh disposable copy or reset worktree of one frozen fixture **and a freshly reset scratch config tree**, with the same cwd and no state inherited from an earlier trial — headless runs write session state into the config tree, so the reset covers both surfaces, keeping trials independent within an arm. Trial output and logs write outside the fixture. A mutating probe without a disposable fixture is `not run`.
- **Blinding and grading:** use neutral arm names and keep the arm map outside trial-visible paths. Trial prompts do not contain the expected skill names, assertions, arm identity, or intended answer. A scorer blind to arm grades captured outputs against the sealed observable rules; inspect the produced artifacts for arm or intent leaks before unblinding.
- **Observable events:** `take` means a captured assistant `tool_use` block naming the exact target Skill. `offer` means the response explicitly names the target invocation token and proposes a clear handoff; a generic suggestion such as “add tests” does not count. The mid-task probe requires an actual take. The seam probe accepts a take when the sealed per-trial authorization key authorizes continuation or an offer when it does not. The sealed key is derived from the trial prompt's own authorization language and must be consistent with it — a prompt the pilot shows ambiguous between take and offer is redesigned, not sealed. The composition probe requires both target skills to be taken or explicitly offered under the same authorization rule.
- **Unsealed pilots:** before sealing, run a cheap paired pilot for every probe — the three positive probes here, the negative probes per the calibration bullet — using separate pilot-only tasks. Confirm the roster, observable event, scoring key, baseline rate, and absence of ceiling — and, for the seam probe, that both arms reliably reach the in-session skill completion at all. If a channel is empty, ambiguous, or ceilinged, redesign it or drop it to characterization-only; do not seal it and do not treat inconclusive as GO.
- **Probes:** (1) *mid-task re-check* — the agent is underway when a finding changes what the work needs, such as discovering an untested legacy module that must be characterized before the refactor; (2) *seam handoff* — the trial task is a failing behavior whose cause is unknown, so the fixed request-time terrain (identical in both arms) routes the agent into `diagnose`; the scored moment is that invoked skill completing and naming `tdd`, with the sealed per-trial authorization key fixing take versus offer. A trial where no skill is invoked and completes in-session never reaches the seam: it is invalid and re-run, symmetric across arms with invalidity rates reported, because a prompt-handed cause would exercise the request-time moment this design disowns; (3) *composition* — findings span authorization and untrusted-input design and require both owning skills. There is no request-time probe.
- **Negative controls (calibration gate):** over-firing is this design's primary introduced risk, so GO also requires a sealed no-overfire result, not only positive uplift — the methodology's calibrated/net-protective verdict, not just load-bearing. Three paired negative probes mirror the obligations: (N1) a mid-task finding that does not change what the work needs — correct behavior is no new skill take; (N2) an invoked skill completes naming a follow-on the trial prompt does not authorize — correct behavior is an offer, never a take (this also guarantees the sealed seam key set includes unauthorized trials); (N3) a task touching several concepts but still owned by one skill — correct behavior is single-skill work without composition. Each sealed negative key lists which takes or continuations count as overfire; grading stays blind under the same observable rules. Gate: at final counts the ON arm's overfire events must not exceed the OFF arm's on any negative probe; an ON-arm excess returns the corresponding clause and the combined block for redesign. Negative probes get the same unsealed pilot treatment — confirm each scenario is unambiguously gradeable and measure the OFF-arm overfire base rate; a negative channel still ambiguous after redesign leaves the calibration gate unmet, and the gate cannot be waived or dropped to characterization-only.
- **Trials and escalation:** start with 3 trials per arm per probe, positive and negative. An arm-map-holding script — never the scorer — tallies the blind grades per arm; if either arm splits 2–1 (or, on a negative probe, the arms' overfire counts differ by exactly one), extend both arms for that probe to 5 before any unblinding. First-round grades stand unchanged and the scorer blind-grades only the added trials under the same sealed rules; the scorer can infer that an escalation occurred, an accepted bounded leak since arm identity stays hidden.
- **Sealed schedule:** the preregistration commits a seeded, arm-interleaved run order across all probe/task cells before execution, executed by the arm-map-holding script with the pinned CLI binary and model selector for every trial, so transient backend or runtime conditions cannot correlate with arm identity.
- **Pass criteria (positive probes):** at 3 trials, the with-arm must satisfy the observable rule in at least 2/3 trials and strictly exceed the without-arm. After escalation, it must satisfy the rule in at least 4/5 trials — preserving the initial two-thirds floor — and strictly exceed the without-arm.
- **Ceiling and aggregation:** any sealed without-arm ceiling is **inconclusive-by-ceiling**, not a pass. GO for the complete contract requires all three positive probes to pass **and** the calibration gate to hold. A fail or inconclusive result returns the affected clause and the combined block for redesign and re-run; results from the other probes may be retained as bounded evidence but cannot authorize the full block.
- **Seal:** after pilots are resolved and an adversarial preregistration review is complete, commit the full preregistration — fresh sealed tasks, arm construction, hashes, fixtures, roster, observable scoring, negative-control keys, the seeded schedule, the environment-surface record, blinding, trial counts, escalation, ceiling, and aggregation. The commit SHA is the seal; pilot tasks and outputs are excluded from sealed scoring, and there is no post-hoc adjustment.
- **Honest bound:** these probes exercise Claude-side behavior. Codex receives the same narrowed text, with behavior bounded initially by source inspection and the live watch rather than represented as experimentally proven. The probes are also same-model — Claude-graded-Claude, methodology moves 4 (cross-model) and 5 (human judge) unused — so per the methodology's honest-limits line this evidence must be weighted accordingly: the take rule stays near-mechanical (a `tool_use` block naming the exact skill) to shrink the judgment surface, and the offer-grading residual is owned explicitly at the step-5 adversarial prereg review.

## Data-Layer Behavior Proof

Structural validation is necessary but does not prove the new exits are followed. After the skill edits, run a documented representative matrix, with one live invocation, forward test, or realistic dry run for every changed skill where practical and an explicit justification where it is not:

- **Sequential exits:** exercise at least `diagnose` → `tdd` → `keep-green`, `test-trust-audit` → `characterization-tests` → `simplify-code`, `postmortem` → `runbook-authoring` (chain 5), and `observability-instrumentation` → `deploy-plan` → `outcome-check` (chain 6).
- **Permissioned offers:** show that a handoff is offered rather than taken when the current request or governing skill stops continuation.
- **Parallel composition:** exercise `red-team` → `authorization-design` + `injection-safe-inputs` without treating composition as automatic agent fan-out.
- **Runtime-conditional exits:** verify the chain-7 wording names Claude-only skills only when available and does not create a false Codex route.
- **Description trigger:** test the `making-recommendations` thin-field → `ideate` description change against should-trigger and nearby should-not-trigger prompts.
- **Plugin-distributed behavior:** test `scrutinize-skill` at source before publication; if JP later authorizes Class-B publication, separately prove the version bump, Codex cache, and mirror rather than treating source behavior as cache proof.

Record the matrix as a target-to-scenario coverage table naming every touched skill (`diagnose`, `tdd`, `test-trust-audit`, `red-team`, `postmortem`, `observability-instrumentation`, `deploy-plan`, `behavior-smoke-test`, `scrutinize-skill`, `making-recommendations`) with its scenario or an explicit impracticality justification, plus commands or prompts, outcomes, and proof limits in the implementation evidence. A parse, integrity check, delivery check, or cache check cannot substitute for these behavior observations.

## Risks Owned

- **Over-firing** — the contract pushes toward invocation after mid-task findings; misrouting is a failure JP does not currently have. Guards: the mid-task-only trigger, "plausibly," the silent check, authorization-aware handoffs, and the precedence clause. Detectors: the sealed negative-control calibration gate pre-landing, and the watch below post-landing. Purely editorial corrections may land without re-running Admission; any change to ownership, obligations, thresholds, carve-outs, or runtime scope is a new gated change and returns to the charter.
- **Subagent exposure** — priced in the Charter Package above.
- **Request-time silence stays unowned** — the observed request-time silence failures sit outside the narrowed contract by design (Non-goals: fixed runtime terrain), and this design does not fix them; accepted residual, so the 2026-08-01 watch reads recurrences as terrain behavior, not contract failure.

```markdown
## Skill Use

- When a mid-task finding changes what the work needs, re-check whether an available skill owns the newly revealed work; when one plausibly fits, invoke it rather than improvising the same job unaided. The check is silent — don't narrate it.
- When an invoked skill completes and names a follow-on lane — an exit, handoff, or next-step pointer — take it only when the current request and governing skill authorize continuation; otherwise offer it explicitly. Don't drop the chain and improvise the next step.
- When a task or its findings span more than one skill's job, compose the skills rather than stretching one past its boundary. Composition may be sequential or concurrent, but it does not itself authorize subagent fan-out.
- A governing skill's explicit stop, containment, or sequencing instruction overrides these defaults, and delegated agents follow their brief.
```
