Best: **Poll the catalog hourly during the day and only assemble at night**
Why: The stated top value is delivering by 06:00 every night, not a faster average night, and the misses (including four timeout kills) point to a long, variable step landing inside the deadline window. This option takes the catalog fetch, which the field names as the long step, out of that window entirely, so a slow Corvid day has all day to finish and the night job becomes minutes. It needs no supplier agreement, no new third-party service, no API feature that may not exist, and no larger machine, so it clears all three hard constraints and the ten-percent spend limit. A local catalog store plus a scheduled poller is machinery a team of three can maintain, and it fits one engineer at half time. Slicing the catalog so it cycles several times a day keeps freshness close to what a five-hour nightly fetch gives today.
Runners-up, in order: **Fetch only items changed since the previous night**, **Run the pricing aggregation concurrently with the catalog fetch**, **Start the job earlier**
Unknowns that would change the choice: The case never states where the hours actually go; if the pricing aggregation or the file writes dominate rather than the fetch, hourly polling gains little and the concurrency or machine options move up. If the partner contract requires catalog data fresher than a few hours at delivery, daytime polling could breach it and the incremental fetch would be preferred. If the Corvid API does support a changed-since filter and the fetch is bounded by request volume rather than API slowness, the incremental option becomes a close rival with less new machinery.
