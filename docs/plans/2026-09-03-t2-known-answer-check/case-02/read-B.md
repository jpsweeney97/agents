Best: **Isolate the integration shards' databases**
Why: E1 and E2 together place 181 of the 200 non-defect failures in the integration stage's setup migration, where four shards each run `bin/migrate` against one shared Postgres service, which is exactly what produces "relation already exists" and "deadlock detected" before any test body runs. E5 shows the ten flakiest tests pass 200 of 200 when run alone, E7 shows the failure rate tracks shard count (4% at one shard, 18% at two, 30% at four), and E6 and E8 rule out resource pressure, dependency drift, and cache misses, so the cause is shared-database contention, not test defects. E3 shows the installed framework (5.4) already supports `database_per_worker: true`, which creates and migrates a separate database per shard, so the fix is a small configuration change well inside two engineer-weeks, keeps runner cost flat, and preserves the 17-minute pipeline inside the 20-minute budget (E7, E10). Removing the 181 setup failures leaves about 19 of 200, roughly 3% of runs, under the 5% target, and those residuals (E1, E6) trace to third-party staging degradation rather than the pipeline. Retry is ruled out by E4 (doubled integration minutes, engineers stopped reading failures), reducing shards by E7 (two shards already push the stage to 21 minutes), mocking and rewrite by E9 and the two-week limit, and the quarantine options treat a symptom when E1 names the cause.
Runners-up, in order: **Fix the ten flakiest tests by hand**, **Reduce the number of shards**, **Add a flaky-test detector that quarantines on repeat failure**

Whether creating and migrating four databases in parallel adds enough time to push the 11-minute integration stage or the 17-minute pipeline past the 20-minute budget.
