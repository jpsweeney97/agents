# Authenticate deliberate modules as direct method surfaces

When the `deliberate` validator is decomposed, every behavior-bearing imported production module will be listed directly in `validation.method-surfaces` alongside the stable `scripts/deliberate-validate.py` entrypoint, and every such file will be platform-hashed before any helper invocation. This extends the existing exact per-file pin, read-authorization, capsule-validation, and restart-frontier mechanism without adding an aggregate-identity layer; the evidence and compatibility boundary are recorded in the [validator debt scan](../audits/2026-07-15-deliberate-validator-debt-scan.md).

## Considered Options

- **Direct per-file inclusion — chosen.** It preserves the current file-grain identity model, keeps drift attributable to a concrete locator, and reuses exact-set validation plus the existing stage-frontier machinery.
- **Aggregate module identity — rejected.** It would add manifest construction and verification machinery, make file-level drift indirect, and create a second authentication abstraction without an observed need.
- **Import modules without pinning them — rejected.** Behavior would execute outside the authenticated method identity and weaken the bootstrap and recovery boundary even if the test suites stayed green.

## Consequences

- The first physical module extraction is contract evolution under `contract-data-version` 6, not a behavior-preserving file move. The version gate, exact `method-surfaces` inventory, and every affected rendering, fixture, test, and runtime instruction must change together.
- Pre-topology capsules carrying the current seven-surface inventory are unsupported and receive no migration path. This hard cut is accepted because no user-valued legacy capsule population exists, including pasted capsules outside the workspace.
- Membership in `method-surfaces` is necessary but not sufficient for bootstrap authentication: the orchestrator must platform-hash the entrypoint and every imported production module before starting the helper, because Python imports execute before helper-owned validation can run.
- Source hashing authenticates executed code only when stale bytecode can neither be created nor read anywhere Python looks: a cache entry whose header matches the source's size and mtime executes in place of the hashed source, silently — proven for repo-local `__pycache__` in the [2026-07-15 gate-1 spike](../smoke-tests/2026-07-15_deliberate-gate1-dual-path-layout-spike.md) (Pass 1b), and proven again inside a reused `sys.pycache_prefix` by the 2026-07-15 follow-up probe (a same-size source edit with restored mtime executed the previous invocation's cached code). Redirecting the cache does not neutralize the hazard; freshness does. The v6 entrypoint must set `sys.pycache_prefix` to a freshly created, initially empty, invocation-private directory outside the repository before importing any first-party module; a prefix is never reused across invocations, and the entrypoint owns its retirement (create it under the process temp root, remove it at exit — an abandoned prefix is harmless only because nothing ever reuses one). The v6 cut's verification must show all five: seeded stale repo-local bytecode is ignored, the chosen prefix starts empty, a second invocation cannot execute the first invocation's cached code, no repo-local bytecode is created or read, and a seeded sourceless `.pyc` beside the production modules triggers the pre-import fail-closed refusal without executing — each exercised through both the canonical in-place path and the Claude symlink path, recording the effective interpreter.
- A fresh cache prefix governs only bytecode Python would create or refresh; it does not stop bytecode Python merely reads. A sourceless `.pyc` sitting directly beside production modules loads through the sourceless loader with the prefix untouched — proven by the 2026-07-15 re-review probe: with a fresh, initially empty, invocation-private prefix in force, CPython 3.13.12 executed a seeded `scripts/_deliberate_hidden.pyc` and the prefix stayed empty before and after. The v6 entrypoint must therefore also run a fail-closed pre-import census of `scripts/` before importing any first-party module, mirroring the gate-2 layout rules, and refuse to run — nonzero exit, no first-party import — when any unexpected artifact is present: any symlink, any `__pycache__` entry, any bytecode or extension-module file, any zip-format archive (by suffix `.zip`/`.egg`/`.whl` and by zip structure — a valid archive is caught even behind an inert suffix or an arbitrary prefix, loadable through zipimport), any directory outside the declared data allowlist, or any nested or non-conforming `.py`.
- Each new module must be classified through the existing method-pin restart-frontier mechanism. The default remains Generate unless a narrower stage is justified and represented in the canonical frontier map.
- Test-only harnesses and fixtures remain outside `method-surfaces`; they prove behavior but do not become authenticated production inputs.

## Rollout Boundary

CH-2 may proceed before the topology gates only while every extraction remains inside `scripts/deliberate-validate.py` and `method-surfaces` stays unchanged.

Before the first physical module extraction, both of these gates must pass:

- An exact-layout dual-path spike must exercise the intended module location and import syntax through the existing PEP 723 entrypoint from the canonical in-place skill path and the Claude symlink path. Both invocations must resolve the intended canonical module and return the same exit status and stdout/stderr for the selected smoke command; a generic throwaway layout is not sufficient evidence.
- An external, non-executing check must compare three independently derived sets and require exact pairwise equality: the root-inclusive transitive first-party Python import closure derived from source, the Python subset of `method-surfaces`, and every production `.py` file physically present under `scripts/`. The same check enforces the complete `scripts/` layout fail-closed: the entrypoint plus flat `scripts/_deliberate_<domain>.py` regular files only; a full recursive census rejects every symlink (file or directory, including symlinked packages), every `__pycache__` entry, every bytecode or extension-module artifact (the loader-suffix model comes from `importlib.machinery.all_suffixes()` plus the cross-platform forms the running platform does not register), every zip-format archive — by suffix (`.zip`/`.egg`/`.whl`) and by zip structure, since a disguised-suffix archive (`payload.dat`) added to `sys.path` imports as code through the zipimport path hook without naming any banned identifier, so the census tests otherwise-inert files with `zipfile.is_zipfile`, which locates the trailing end-of-central-directory record the way zipimport does and therefore catches a prefixed/self-extracting archive whose first bytes are not `PK` (a four-byte magic sniff missed this; corrected 2026-07-16, see the addendum below) — every directory outside the declared data allowlist (currently `fixtures/`, itself recursively subject to the same artifact rules), and every nested, non-conforming, or dotted-import first-party `.py`; and a statically imported name with any local presence other than its inventoried flat source — a sourceless `.pyc`, a package directory, a symlink — is rejected rather than classified as third-party. Dynamic-import and code-execution machinery is rejected by a positional identifier ban (`__import__`, `__builtins__`, `builtins`, `importlib`, `zipimport`, `runpy`, `exec`, `eval`, `compile`): a banned name used as an identifier (`ast.Name`) or as an imported module or symbol (`import` / `from ... import`) fails the check, so bare, alias, and attribute spellings that must name the machinery cannot bypass it. The ban deliberately does not scan attribute names or string literals, so ordinary `re.compile` or the word "eval" in a docstring is not a false positive; the security burden for that narrowing rests on the census, not the ban. Reaching import or exec machinery still requires naming a banned identifier or a reflection gadget (`().__class__.__bases__`, `globals()['__builtins__']`, a computed import string); that gadget/computed-string residual is statically undetectable by design and is accepted, backstopped by the census guarantee that no loadable Python artifact sits uninventoried under `scripts/` for such a gadget to reach. Native-code loaders (for example `ctypes` loading a shared library) execute outside the Python-module import graph and are outside this gate's authentication boundary. Together the census and the ban keep the static closure authoritative: no dynamically reachable Python file can sit outside the authenticated identity while the gate is green. The check must not import the entrypoint or any production module, because executing imports before the comparison would cross the authentication boundary it is meant to guard. This authoring gate detects inventory omission, dead inventory, on-disk orphans, and layout violations; platform hashing remains the runtime authentication gate for inventoried files.

The first physical extraction is `scripts/_deliberate_shared.py`: the shared error/refusal constructors, read-authorization, and safe-YAML loading foundation — the smallest coherent domain, the base of the internal dependency graph (everything calls into it; it calls into no other first-party code), so the v6 machinery rides the smallest, lowest-semantic-risk payload. Its restart frontier is the existing `default` (Generate); v6 adds no frontier-map entry and therefore no frontier-shape change to the validator. Module naming rule: production modules are `scripts/_deliberate_<domain>.py`, and no module may take the top-level name of any stdlib or third-party import the bundle uses, because script-directory resolution makes a local module shadow the installed package. Production modules are flat regular files — no packages, no symlinks, no adjacent zip archives — and never name dynamic-import or code-execution machinery (any identifier in the gate-2 banned set, used as a name or import). The import-closure check enforces the naming rule, the complete layout census, and the identifier ban directly, whether or not the offending file is inventoried.

Failure or absence of either gate blocks the v6 physical extraction, but does not block in-file CH-2 simplification.

## Amendment (2026-07-16): import-boundary policy contract — placement and runtime mechanism

Option 2 of the landed hardening portfolio ([docs/hardening/2026-07-16-deliberate-import-boundary/](../hardening/2026-07-16-deliberate-import-boundary/hardening.md)) governs the v6 cut: the import-execution boundary is owned by one declarative policy contract, and drift between its consumers is mechanically visible. JP decided the placement on 2026-07-16: the policy lives in the already-pinned `references/contract-data.yaml` as a top-level `import-boundary` section — not in a new pinned surface (surface-set expansion declined) and not in an unpinned adjacent reference (rejected by the portfolio's review fold). The policy is therefore hash-authenticated with the rest of the method identity, and policy edits classify under the existing method-pin drift rules: value-neutral edits become restart frontiers; surface-set, bounds, schema, or tightened-value changes are hard compatibility cuts.

The runtime mechanism is embedded values, never an invocation-time policy read. The entrypoint embeds the census-consumed policy subset as constants; the module-level pre-import preflight uses only those embedded values, with only startup-initialized stdlib (`os`, `sys`) imported before the census so no shadowable import precedes it; and every contract load compares the embedded rendering against the contract's `import-boundary` section, refusing on any difference — so the runtime never reads an unpinned policy reference as authority and a drifted rendering cannot survive an invocation unnoticed. A pre-import `yaml.safe_load` of the policy was considered and rejected: it would route the first parse of a pinned surface through a weaker parser than the validator's event-checked loader (aliases, anchors, byte and depth caps unenforced before the safe parser is importable), and duplicating the event-checked parser into the pre-import section would defeat the extraction that motivates v6. The Gate-2 authoring checker consumes the same contract section directly. The identifier ban stays authoring-time enforcement and is not embedded in the runtime; a policy-floor regression test guards the known hazard values against accidental weakening. The policy contract lands inside the single v6 cut as one `contract-data-version` bump to 6, not as a separate pre-v6 gate: the validator's exact top-level key set means the section cannot land additively under version 5, and a second bump would double the capsule hard cut for no benefit.

Implementation is planned in [docs/plans/2026-07-16-deliberate-v6-shared-module-extraction.md](../plans/2026-07-16-deliberate-v6-shared-module-extraction.md).

## Addendum (2026-07-16): execution-readiness scrutiny corrections

An execution-readiness scrutiny of the v6 plan reproduced a live Gate-2 bypass and surfaced a runtime-ordering contradiction. Both are resolved here; the amendment above stands except as corrected below.

**Zip detection is structural, in both consumers.** A structurally valid zip carrying an arbitrary prefix (a shell or self-extracting stub whose first four bytes are not `PK`) imported through zipimport while the Gate-2 census — which sniffed only the first four bytes — passed it green. The census now detects zip archives by structure via `zipfile.is_zipfile`, which locates the trailing end-of-central-directory record the way zipimport does; the four-byte magic list is removed. The live Gate-2 checker was repaired (commit `43065ca`, with a mutation-proven prefixed-zip regression) before the v6 cut proceeds, and the v6 runtime pre-import preflight carries the same detector. Because the runtime preflight cannot import `zipfile` until it has proven no importable shadow exists under `scripts/`, it runs in two passes: pass 1 enforces every layout rule on startup-initialized stdlib (`os`, `sys`) alone and collects the inert-suffix files; once pass 1 refuses nothing, importing `zipfile` cannot resolve to a `scripts/` file, and pass 2 tests the collected files with `is_zipfile`. The two consumers therefore share one detector and cannot drift on zip detection. There is no `zip-magics` policy value.

**Embedded-vs-contract authentication is release-time; the per-invocation compare is post-import defense-in-depth.** The amendment above says every contract load compares the embedded rendering against the contract section. That per-invocation compare (`_require_boundary_match`) necessarily runs *after* the first-party import, because a genuinely pre-import runtime match is circular under this cut: the match needs the contract parsed, contract-loading uses `safe_parse`/`ReadSet`, and those are exactly the code being extracted into `_deliberate_shared` — and the weaker pre-import `yaml.safe_load` route was already rejected. The security invariant ("no unauthenticated Python executes before method-surface identity is established") is met without a pre-import runtime match: (a) the embedded census policy lives in the entrypoint source, so it is authenticated by the entrypoint's own method-surface hash — trusting the entrypoint is trusting its embedded census; and (b) a non-executing release-time test asserts the embedded `_BOUNDARY_POLICY` equals the contract's `import-boundary` section (minus `banned-identifiers`), so a desynced pair cannot ship. `_require_boundary_match` then adds per-invocation defense-in-depth against a contract swapped via `--data` at runtime. This is a consciously accepted boundary that is weaker than a hypothetical pre-import runtime equivalence check and stronger than an unauthenticated embedded copy; the "before first-party import occurs" language in the hardening proposal is reconciled to mean this release-time authentication (the proposal is amended to match). The stronger form would require either duplicating the event-checked parser pre-import (defeating the extraction) or extracting a leaf module instead of the shared foundation (a different v6 cut); neither is adopted now.

## Revisit When

Reconsider aggregate identity only if the direct inventory becomes operationally unmanageable, a transitive import can no longer be enumerated before execution, or a real legacy capsule population creates a migration requirement.
