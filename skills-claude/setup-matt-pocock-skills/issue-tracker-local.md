# Issue tracker: Local Markdown

Issues and PRDs for this repo live as Markdown files under `.scratch/`. There is no tracker service and no CLI: every tracker operation is a file operation, defined below so the skills that publish, triage, and pick up issues behave the same way every time.

## Layout

- One feature per directory: `.scratch/<feature-slug>/`
- The PRD is `.scratch/<feature-slug>/PRD.md`
- Implementation issues are `.scratch/<feature-slug>/issues/<NN>-<slug>.md`, numbered from `01`; the next number is one more than the highest number already in that directory
- An issue's identifier is its path. Inside one feature, the number alone is enough (`issue 03`); across features, use the path. There are no URLs.
- `.scratch/` is committed. _(Change this line to "`.scratch/` is git-ignored" if you chose not to commit it; an ignored tracker keeps no history and cannot be reviewed.)_

## Issue file shape

Every issue file and PRD starts with a title heading and a header block, then the body, then a `## Comments` section. Skills read and edit the header lines, so keep them exactly in this form, one per line, directly under the title:

```markdown
# <Title>

Status: needs-triage
Category: enhancement
Created: 2026-09-04

<body: for an implementation issue, the `to-issues` issue template — What to build, Acceptance criteria, Blocked by, and Parent when there is one>

## Comments
```

- `Status:` holds exactly one of the five triage-role strings from `triage-labels.md`, or `closed` (see Closing an issue). A file with no `Status:` line is unlabeled: never triaged.
- `Category:` holds exactly one of the two category-role strings from `triage-labels.md` (`bug` or `enhancement`). A PRD may omit it until triage assigns one.
- `Created:` is the date the file was created, used for oldest-first ordering. When it is missing, order by number.
- An issue or comment that a skill generates during triage starts with the `> *This was generated by AI during triage.*` line: above the title for an issue file, as the first line of the comment body for a comment.

## Conventions

- **Create an issue**: write a new file at the next number under `.scratch/<feature-slug>/issues/`, creating the directory if needed, with the header block above. Stage new files by explicit path.
- **Read an issue**: read the whole file. Everything under `## Comments` is the comment history, oldest first; later comments amend the body.
- **List issues**: search the `Status:` lines of both PRDs and issues. `grep -l '^Status: ready-for-agent$' .scratch/*/PRD.md .scratch/*/issues/*.md` lists one role; `grep -L '^Status:' .scratch/*/PRD.md .scratch/*/issues/*.md` lists unlabeled items. "Oldest first" means by the `Created:` line, then by number, then by path.
- **Comment on an issue**: append to the end of the file, under `## Comments`, as a `### YYYY-MM-DD — <who>` heading followed by the comment body, where `<who>` is the skill that wrote it (`triage`, `implement-issue`) or the person's name. Never edit or delete an earlier comment.
- **Apply / remove labels**: a label is the value of the `Status:` or `Category:` line, not a tracker-side object. Applying a state role replaces the `Status:` value; applying a category role replaces the `Category:` value. Removing a label means replacing it: a triaged issue never has an empty `Status:` or `Category:` line.
- **Close**: set `Status: closed` and append a closing comment (see Closing an issue). `wontfix` works the same way: `Status: wontfix` plus its comment.
- **Parent and blockers**: there are no native issue relationships. Use the text `## Parent` and `## Blocked by` sections from the `to-issues` template, and write each reference as a relative Markdown link (`[issue 03](03-split-schema.md)`, `[PRD](../PRD.md)`), never bare prose, so the link resolves.
- **Is a blocker closed?**: follow each link under `## Blocked by` and read that file's `Status:` line. A blocker is closed only when its status is `closed`. A blocker at `wontfix` is not closed: the dependent issue's premise is gone, so report the contradiction instead of treating the issue as unblocked.
- **Existing-issue check on a resumed run**: before creating an issue, compare its title against the `# ` title lines of the files already in the same feature directory; on a match, update that file instead of creating a duplicate.
- **Reporter activity since the last triage notes**: any comment under `## Comments` that comes after the most recent comment beginning with the triage disclaimer line.

## Closing an issue

When the issue's stated scope is complete, set `Status: closed` and append a comment naming the result and its evidence. `closed` is a lifecycle state, not a sixth triage role: it means no work remains within the issue's stated scope. Do not use `wontfix` for completed work; it means the issue will not be actioned. Never delete an issue file to close it.

## Pull requests as a triage surface

Not applicable. A local Markdown tracker has no pull requests, so `/triage` reads only issues. A bare number such as `#42` means issue `42` of the feature under discussion; when more than one feature directory has that number, ask which one.

## When a skill says "publish to the issue tracker"

Create a new file under `.scratch/<feature-slug>/` with the header block above, creating the directory if needed. A PRD is `PRD.md` with `Status: needs-triage`; an implementation issue is the next numbered file under `issues/`.

## When a skill says "fetch the relevant ticket"

Read the whole file at the referenced path. The user will normally pass the path or the issue number directly.
